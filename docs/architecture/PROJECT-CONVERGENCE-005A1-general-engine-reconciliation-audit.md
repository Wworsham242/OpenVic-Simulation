# PROJECT-CONVERGENCE-005A1 — General Engine Reconciliation Audit

## Scope

Reconnaissance at `8a195eb1a52f4df01b7ef011d5a7f2e86aaa2d62` (`PROJECT-CONVERGENCE-004A12 add canonical demographic TSV import`) on `work/live-economy-005-modern-catalog`, 2026-09-10. Local HEAD and the authoritative remote branch both matched that commit before this audit. The working tree was clean.

This is an architecture assessment, not an implementation proposal for a replacement engine. It inspects every requested subsystem, identifies existing authority and limitations, and performs the specified modern/Bronze Age architecture test. Neither scenario is built. No production code, tests, legacy content, or authoritative state is changed.

Conclusion: the repository contains a substantial reusable runtime and physical-economic chassis, but it is not yet a fully general, data-assembled strategic-world engine. Generic mechanisms coexist with mandatory country/POP/geographic schemas, a land/naval military type system, incomplete scripting execution, and a deliberately bounded native bootstrap. These are distinguishable from missing specialist capabilities; missing banking or intelligence is not evidence that the scheduler or inventory machinery should be replaced.

## Architectural Target

The target is mechanism-rich and ontology-light. Time, deterministic scheduling, stable identity, registries, authoritative ownership, stocks, flows, transformations, transactions, location/network references, orders, observation, and persistence should be reusable. Political entities, population dimensions, institutions, sectors, goods, technologies, military capabilities, geography granularity, and calculations should be defined by each game wherever the existing mechanism permits.

For each matrix row the counterfactual question is: would this mechanism still be chosen for a strategic-world simulator if Victoria, EU, HOI, and OpenVic had never existed? An affirmative answer about a primitive does not certify all its current callers. Different worlds may use different formulas. A genuinely new mechanism may require C++; renaming a period-specific entity should not.

Capability must not imply mandatory state or resolution. The absent demographic structures in `PopDemographicAgeSexState` and `ProvinceDemographicAgeSexState` demonstrate this distinction. The hard-coded socioeconomic fields in `PopBase` demonstrate where it is not yet achieved. No universal causal graph, ECS-only storage requirement, parallel population ledger, or new world owner is proposed.

## General Core Already Present

- `core/simulation/SimTime.hpp` provides integer ordered time and `checked_advance`; `Cadence.hpp` supplies validated periodicity and stable semantic staggering. Neither requires a historical setting.
- `SimulationEventScheduler.hpp`, `SimulationTimeline.hpp`, and `OrderedCommandRuntime.hpp` preserve scheduled-event ordering, timeline continuity, accepted-command sequence, and replay position. These are different responsibilities and should remain separate.
- `ecs/SystemScheduler.hpp/.cpp` owns conflict-aware stages and schedule hashing; `ecs/World.hpp/.cpp` owns entity lifecycle and identity restoration. `tests/src/ecs/FoundationTimingIntegration.cpp` demonstrates composition with timing without making ECS the sole storage model.
- `types/IdentifierRegistry.hpp`, `TypedIndices.hpp`, `IndexedFlatMap.hpp`, and `fixed_point/FixedPoint.hpp` provide reusable identity, indexed storage, and deterministic numerical machinery. Numeric range and registry lifetime contracts still matter.
- `AuthorityRegistry::authorizes` and `CommandAdmissionRuntime::submit` use opaque actor/command/jurisdiction identifiers. `player/PositionIdentity.hpp` separates the authority-bearing position from its occupant.
- `AggregateProducer::produce`, `ResourceSupplyNetwork`, `DeliverableSupply`, `MarketNodeAccessTable`, and `LogisticsGraph::allocate_flows` express material constraints through quantities, inventory, and capacity rather than arbitrary production penalties.
- `utility/reactive/DerivedState.hpp` lazily recomputes tracked dependencies. `LiveEconomyProvenance.hpp` exposes results derived from native domain transitions; neither is a universal world-physics graph.

## Country and Political-Actor Findings

`CountryDefinition` is more than an opaque ID: it holds a party registry, graphical culture reference, unit names and government-dependent colors. `is_rebel_country()` identifies index zero specially. `CountryInstance` inherits `PopsAggregate`, references the market and multiple define managers, and maintains the following roles together:

| Role | Concrete current state / seam | Consequence |
| --- | --- | --- |
| Sovereign identity | `CountryInstance::country_definition`, `CountryDefinition::is_dynamic_tag` | Definition/tag identity is not an arbitrary governing organization. |
| Governing authority | `government_type`, `ruling_party`, `rule_set`; separate `AuthorityRegistry` grants | Government data does not itself define a general office/jurisdiction lifecycle. |
| Treasury | `cash_stockpile`, tax/sliding spending state, `FiscalCollectionCapacity` | Fiscal policy and cash live on country even when another institution could collect/pay. |
| Institutions | `reforms`, `upper_house_proportion_by_ideology`, `last_election` | Institution schema is party/election-oriented. |
| Territory | `owned_provinces`, `controlled_provinces`, `core_provinces`, `states`, `capital` | Ownership and control are distinct, but endpoints are countries. |
| Population | Inherited `PopsAggregate`, primary/accepted culture and religion | Country aggregates people geographically; province POP storage owns people, not a second country ledger. |
| Military | Branched unit/group access and mobilization state; `UnitInstanceGroup::country` | Group membership/command identity depends on country and fixed branches. |
| Diplomacy | `CountryRelationManager`, country-pair relationships | A non-state participant currently needs country-shaped representation or a new endpoint seam. |
| Economy | Market reference, foreign investments, industrial-power aggregates, fiscal stockpile | Country coordinates economic policy/reporting; it does not own all producer inventories or a separate market per country. |
| Research | `technology_unlock_levels`, `current_research`, `research_point_stockpile`, `tech_school` | Universities, guilds or other research actors cannot merely be new data entries with independent progress. |

This is a high-coupling object, not proof that all its state is wrong. `CountryInstanceManager` and sanctioned mutation methods should remain authoritative while boundaries are clarified. `country_status_t` explicitly includes GREAT_POWER, CIVILISED, UNCIVILISED and PRIMITIVE; these are compatibility concepts, not categories for a generic actor model. Merely calling a tribal confederacy or corporation a country does not satisfy the counterfactual test. No actor replacement or role decomposition is implemented here.

## Geography and Resolution Findings

`ProvinceDefinition` has stable identity, geometry/positions, terrain and adjacency; these can represent differently sized cells supplied by content. The primitive does not force a particular real-world square-kilometer scale. `PointMap` and `market_node_index_t` are even less committed: a market node can identify a port, region or industrial cluster independently of province hierarchy.

The live hierarchy is not arbitrarily game-defined. `StateManager::generate_states` visits non-meta `Region` definitions; `add_state_set` groups provinces by matching owner and colony status. `State::get_owner` derives its owner from its capital. `ProvinceInstance` links to a `State` and owns POPs, buildings, an RGO and environmental/demographic state. `ProductionType::is_valid_for_factory_in(State&)`, `PopValuesFromProvince`, `UnitInstanceGroup::location/path`, and country territorial sets spread these semantics into economics, population, movement and politics.

`ProductiveSiteBinding::resolve` uses province/building/process identifiers as references to real objects; that identity lookup and installed-capacity calculation can remain. However, `LaborPoolScope` currently has only `ProvinceLocal`. The resolver cannot represent commuting areas, overlapping jurisdictions or a hierarchy of arbitrary depth by content alone. A different province map is supported; a different relationship between administrative, economic and military geography is not yet generally supported.

Preserve province identity, adjacency, non-owning references and aggregate calculations without changing behavior. Future work should test a specific additional grouping before renaming or replacing map classes. Coarse location mechanisms are reusable; one RGO per province and owner/colonial-state partitioning are capability/policy assumptions.

## Population Findings

`PopBase::size` is the native people count. `PopBase` requires `PopType`, `Culture` and `Religion` references and carries militancy, consciousness and rebel type. `Pop` additionally carries literacy, ideological/reform support, votes, monetary needs, income categories and culture-sensitive recruitment compatibility. Data can change the identities and values in these dimensions; it cannot omit or replace the C++ dimension schema. Bronze Age kinship/status dimensions or modern population aggregates are therefore not already arbitrary data schemas.

`PopsAggregate` and `ProvinceInstance::_update_pops` derive totals from actual POPs. Employment is stored in `Pop::employed`, reset during `Pop::tick`, committed through `Pop::hire`, and observed through `get_unemployed`. `WorkforcePool` is a non-owning span/colony adapter. `allocate_competing_employers` orders requests by labor offer and stable employer ID and commits through employer adapters; it does not own a second worker stock. `InstanceManager::tick` prepares employment, gathers live-site requests, invokes `MapInstance::allocate_employment_phase`, applies allocations, and finishes RGO production before the shared market clear. This is stronger integration than the original RGO-first site proof.

Age-sex detail is genuinely opt-in. `PopDemographicAgeSexState` and `ProvinceDemographicAgeSexState` hold nullable heap-backed structures; initialization requires an explicit profile and refuses a second initialization. `materialize_province_demographic_age_sex_profile` reconciles to the native 64-bit aggregate total, rejecting cell overflow. The fixed 18 age bands by two demographic-sex cells are a particular optional capability, not a general dimension registry. Per-POP cross-tabs are not fabricated from province profiles. A future game can leave both structures absent; the presence of the capability does not allocate all 36 counters for every POP.

`ProvinceDemographicAgeSexInput`/`Registry` retain explicit provenance and authority priority; the registry locks before resolving candidate pointers. `ProvinceDemographicAgeSexTsv.hpp` parses canonical records rather than creating world identities or directly modifying provinces. Whole-file ingestion, provider matching and live automatic initialization are not implied by the row parser. The initialized demographic composition is stored detail constrained by the people total; it is not permission to evolve a second total independently. Future births/deaths/migration must maintain POP/province/detail consistency in one sanctioned boundary; current consistency checks are not such a transition mechanism.

Stored versus derived matters elsewhere too. Survival-needs exposure and nutritional health burden carry history in `Pop`; `get_basic_resource_stress_response` derives pressure from that exposure and militancy. The response does not move people or cause deaths. Unlike age-sex detail, stress/burden fields and daily updates are currently present on native POPs without a capability toggle. Their desired classification as optional must not be confused with current storage optionality. The 30-day exposure/deterioration and 60-day recovery parameters in the corresponding headers are provisional calibration, not empirical universal laws.

## Economy and Production Findings

`ProductionType::PROCESS` reuses native recipe identity, goods requirements, output and workforce scale; `AGGREGATE` is an alias. Unlike legacy templates it need not impose a Victoria owner job. `AggregateProducer::produce` calculates output from capacity, utilization, optional workforce and external ceilings, then limits by actual input inventories and consumes inputs/adds output. That mechanism can transform copper/tin into bronze or inputs into semiconductor output with different content. Current recipes have one output good and fixed coefficients; multi-output transformations or substitution require an explicit mechanism extension rather than a cosmetic content change.

`BuildingType::capacity_per_level` and `BuildingInstance` provide an existing facility asset/level source. `ProductiveSiteBinding::resolve` reads actual map-owned building level and validates the process rather than retaining a second facility ledger. `BuildingInstance::expand` still has the construction-cost charging TODO: construction time/requirements in a definition do not establish material or cash settlement. Factory/RGO/artisan executors contain useful reference accounting, but their owner/jobs, farm/mine, subsidy and POP-artisan structure should remain compatibility implementations.

`ProductiveSiteMaterialFlowResolver::resolve` supplies actual inventories using source networks and logistics. `AggregateProducerMarketBridge` creates orders and records actual fills. `GoodMarket::execute_orders` is real clearing, not scripted supply-chain propagation; however, its country-index scratch maps and optional country order attribution, `MarketInstance`'s `CountryDefines` dependency, and built-in price limits mean the current trading stack is not completely ontology-free. `MarketNodeAccessTable` and `DeliverableSupply` constrain access outside clearing. They are not proof of fully source-segregated bilateral settlement or regional banking.

`LogisticsGraph::find_route` selects usable fewest-hop paths with stable edge-ID tie breaking. `allocate_flows` shares physical edge capacities, then tries one residual alternative in stable flow-ID order. `TransportCorridor` and `SharedTransportCapacity` remain available compatibility/coarse paths. These mechanisms support maritime and land throughput in either world; they do not yet model containers, vessels, convoy risk, transit inventories, queues, transport payments or globally optimal multi-commodity flow. Such missing mechanisms do not justify rewriting current quantity conservation.

Electricity is already more than a scalar utility penalty. `ProductiveSiteElectricitySource` stores dispatch history, fuel inventory/consumption, availability, outages, resource availability, ramp/minimum-output characteristics and cost/priority. `ProductiveSiteElectricityGridResolver::resolve_sources_stateful` allocates generation/transmission service. `ProductiveSiteUtilityResolver::apply` converts explicit service requirements into output ceilings; it does not put electricity into ordinary material inventory. This is coarse capacity allocation, not an electrical load-flow solver. `LiveEconomyRuntime::electricity_grid_configured` defaults false; empty utility requirements leave no utility ceiling. Bronze Age production needs no electricity sources or grid, although the optional-capability containers remain members of the live runtime.

`ProductiveSiteOperatingEconomics::calculate` distinguishes market cash facts, actual configured labor compensation, and material/electricity/logistics cost proxies. `ProductiveSiteWageFormation` and `ProductiveSiteUtilizationDecision` supply optional bounded policies. Operating surplus here is not a complete enterprise balance sheet or a transactionally balanced banking system. `CountryInstance::cash_stockpile`, `FactoryProducer::budget`, POP cash and `EconomyDefines` loan parameters are existing money-related state; none establishes a general bank/deposit/credit registry. Likewise, tribute is not automatically a market buy/sell transaction. Finance and tribute settlement require appropriately scoped mechanisms using existing stock owners.

`LiveEconomyRuntime` remains shaped around `upstream`, `downstream`, intermediate/final goods and additional upstream sites bound to the same upstream process. Its integration is real, but it is not yet arbitrary sector-network assembly from data. Keep its production, allocation, market and resource mechanisms; address orchestration limits at their boundary.

## Military Findings

`UnitType` already has identifier, strength/organization/speed, build time, goods build/supply costs and terrain modifiers. `UnitInstance` adds unique identity and current strength/organization. `UnitInstanceGroup` aggregates units, leader, location, owner and movement. `Deployment` supplies initial organizations. These are plausible reusable formation scaffolding.

The current family is closed: `unit_branch_t` has only LAND and NAVAL, `UnitTypeBranched` specializes regiment and ship fields, `UnitTypeManager::expect_branch_str` accepts land/naval/sea, and `Deployment` contains armies/navies. Land instances point to a `Pop`; recruitment restrictions align numerically with `Pop::culture_status_t`. Groups require `CountryInstance` and `ProvinceInstance` references and contain units rather than an arbitrary nested formation tree.

A coarse chariot unit can be described using land-unit data and goods costs, but forcing every chariot organization into regiment/culture recruitment semantics is not a complete generalization. Modern brigades/divisions can be approximated as groups, but aircraft, missiles, sensors, readiness/maintenance beyond current fields, and nested command structures are not delivered by changing unit names. Those expose both ontology constraints and genuinely missing mechanism classes. Generalize the existing identity/group/type boundary through one proof before concluding that military storage must be replaced. No new formation hierarchy, combat model or recruitment ledger is introduced here.

## Authority and Player-Position Findings

`PositionIdentity::authority_actor_id` returns the position ID. `PositionOccupancy` carries controller ID/kind separately, and `PositionSessionBootstrap` installs canonical occupancy/grants. `InstanceManager::submit_occupied_position_command` derives actor and jurisdiction from occupancy; `AuthorityRegistry::authorizes` performs exact grant lookup. Human and AI occupants can therefore use the same authority-bearing position and grants.

This is a real seam toward position control, not complete institutional government. `PlayerManager::set_country` still accepts a direct country pointer. `GovernmentType` describes compatible ideologies, elections, appointment and terms, not offices, delegation, vetoes, succession or institutional budgets. Bootstrap is pre-session; general mid-session appointments/vacancies are not established.

`queue_occupied_legacy_mobilise` bridges admission/logging to the existing legacy mobilization action. Other legacy `GameAction` paths remain. The generalized grant jurisdiction and the payload's numeric country target are distinct; granting a jurisdiction string is not itself a semantic proof that a payload target belongs to it. Future migration must validate the target mapping before acceptance and preserve log/queue/mutation atomicity. There is no justification for a second authority registry or a player-only mutation privilege.

## Information and Perceived-State Findings

The repository has authoritative values and factual explanation, not a general actor-knowledge layer. `InstanceManager::get_live_economy_status` and `get_live_economy_provenance` return truth-derived results. `modifier_entry_t` identifies sources; `Pop` stores recent stress/burden update facts. None supplies observer identity, reporting delay, uncertainty or deception.

Inspection of the requested domain owners and searches for perceived state, observations, beliefs, intelligence and sensors found no integrated actor-specific observation/report store. `RECONCILIATION-001` explicitly defines the desired truth-to-observation-to-knowledge seam and defers implementation. Event news strings and military reconnaissance statistics are not that seam. Do not infer a hidden complete communications subsystem from those names.

Both messenger reports and modern communications/intelligence need delayed, actor-addressed information derived from one world truth. `SimulationEventScheduler` could schedule deliveries and `PositionIdentity` could identify recipients, but the observations, validity timestamps, uncertainty semantics and AI/player consumers are missing. This is a bounded missing capability and integration blocker for those target-world requirements, not a reason to clone worlds per actor or treat provenance as perceived truth.

## Modding and Extension Findings

`Dataloader::set_roots`, `lookup_file`, replace-path handling and `ModManager::load_mod_file` support content overlays/descriptors. `Mod::generate_dependency_list` uses a bounded recursive traversal with a `MAX_RECURSE` failsafe; this is not a general package dependency solver. `Dataloader::load_defines` orchestrates a Victoria-shaped directory/schema dependency order. `GameManager::load_native_economy_bootstrap` proves native content without a Victoria root, but its fixed goods/production/facility/scenario files are an economy vertical, not a complete capability manifest.

Without recompilation, current parsers can define goods, PROCESS recipes and numeric requirements, facilities/capacity, the supported live-economy scenario fields, country/party/government content, existing unit types, technologies/inventions, history and modifier values. This means new entries within known schemas, not arbitrary runtime state or new formulas. Some runtime capability settings are C++ configuration APIs rather than file syntax; an API accepting a struct does not make every field moddable.

`ConditionManager` parses typed conditions and identifiers within fixed POP/PROVINCE/STATE/COUNTRY/THIS/FROM scopes. `ConditionScript::_parse_script` invokes this parser. `ConditionalWeight::expect_conditional_weight` loads base/factor/time and grouped conditional modifiers; `parse_scripts` parses embedded conditions. Crucially, `EffectScript::_parse_script` is a TODO returning true. Neither this success return nor Event/Decision load success certifies executable effects or a general expression evaluator. `RuleSet` is a compiled collection of factory/railway/voting/slavery flags with fixed merge/priority semantics; it is not the desired extensible rules engine.

`ModifierManager::setup_modifier_effects` registers a compiled effect catalog and `ModifierEffectCache` gives native consumers effect pointers. `ModifierSum` composes values with country/province source attribution. Content can select known values; adding a new quantity's meaning or consumer requires C++. Similarly, adding a military branch, population dimension, utility kind, institution procedure, or formula operator currently needs native changes.

The existing parsers/registries can evolve toward data-defined content and restricted formula composition, but only with an explicit evaluation contract: declared typed inputs/results, unit/range validation, deterministic execution, bounded work, and sanctioned output consumers. First prove a read-only calculation; effectful changes must pass domain mutation/admission boundaries. This is a future direction, not a claim of present support or a plan to make scripting the physics of every domain.

## Runtime, Time, Determinism and Provenance Findings

`SimTime::checked_advance`, `Cadence::create/staggered`, `SimulationTimeline` and `SimulationEventScheduler` are an adequate generic time/event substrate. `misc/SimulationClock` handles wall-clock speed/pause separately. `InstanceManager::tick` still advances 24 simulation ticks per legacy day, increments `Date`, then follows a fixed country/employment/production/market/unit sequence. `LiveEconomyRuntime::run_due_daily_cycles` uses crossed cadence boundaries, but other domains are not thereby migrated to arbitrary sub-day cadences. `Date` uses a fixed 365-day calendar; signed internal years do not establish arbitrary game-calendar or every import-format convention.

`ecs/SystemScheduler` separates conflict ordering from `System` run predicates, with invalid schedules executing no systems and a zero hash. `World` identity snapshots preserve slot/generation/free-list identity, not arbitrary component payload persistence. The live instance also uses traditional specialist managers and `utility/ThreadPool`; ECS invariance tests are not a blanket full-runtime determinism proof.

`DeterministicRngManager::next_u64` isolates named streams and `capture_state`/`restore_state` preserve them. `InstanceManager` does not yet own all gameplay RNG through this generalized interface; `Pop` still takes `RandomU32`. Therefore replay infrastructure exists, but complete named-stream migration cannot be claimed.

`OrderedCommandRuntime` owns accepted sequence and replay cursor. `LiveCommandTimelineState::capture/restore` composes timeline and command continuity transactionally. `CampaignStateSnapshot` contains timeline, RNG records, command log/replay and ECS identity; it does not contain native country treasuries, POPs, demographic profiles, environmental state, producer inventories, electricity dispatch/fuel state or all authority/occupancy state. A saved command cursor is not a saved campaign or replay-to-identical-world guarantee.

`MutableState`, `DependencyTracker` and `DerivedState::recalculate_if_dirty` support reactive dependencies and cached recomputation; dependencies must actually be tracked. They are not automatic cross-domain causal scheduling. `LiveEconomyRuntime::get_latest_provenance` exposes the latest completed cycle with physical, employment, production and clearing facts. Recording does not own simulation outcomes. Coverage is bounded to this vertical, not a universal persistent causal graph or a source of actor beliefs.

## Architectural Blockers

Only barriers to the stated architecture are listed here; incomplete specialist detail alone is not a core-design failure.

1. **Independent actor roles cannot be assembled through data.** `CountryInstance`, `CountryRelationManager` and `UnitInstanceGroup` couple authority-bearing entities to country-shaped fiscal, military and diplomatic state. `PositionIdentity` solves controller identity but not these domain endpoints.
2. **Population and administrative resolution are fixed schemas.** `PopBase` requires particular dimensions; `StateManager::add_state_set` partitions on ownership/colonial status; `LaborPoolScope` exposes only `ProvinceLocal`. Arbitrary game dimensions/groupings cannot be content-only choices.
3. **Military capability classes are closed.** `unit_branch_t`, branched types, manager storage and `Deployment` cannot accept aircraft/missile or arbitrary organizational capabilities merely as data.
4. **General native assembly and calculations are incomplete.** `GameManager::load_native_economy_bootstrap`, fixed `LiveEconomyScenario` roles, `Condition` scopes and the `EffectScript` TODO prevent the requested breadth of content/rule assembly without C++ edits.
5. **Full authoritative continuity is not composed.** `CampaignStateSnapshot` and `LiveCommandTimelineSnapshot` omit native domain state and parts of command authority context. General campaign save/replay cannot be claimed from their existing coverage.
6. **The requested information boundary has no implementation owner.** `InstanceManager` status/provenance returns truth, while actor observations, reports and knowledge consumers remain deferred in `RECONCILIATION-001`. Both communications requirements therefore need a first vertical.

Banking/financial claims, tribute settlement, detailed weather/hydrology, transit queues, electrical load flow and advanced combat are missing or limited capabilities, not evidence of fundamentally unusable generic cores. Their absence limits full scenario capability and is recorded in the two-world results. No replacement of existing authority is justified merely to add them.

## High-Risk Couplings

- **Country pointer fan-out:** country endpoints appear in territory, POP-derived values, diplomacy, military, history and modifiers. Changes to `CountryInstance` identity can cascade across all of these; introduce a proven boundary before moving state.
- **Location as domain owner:** `ProvinceInstance` owns POPs/RGO/buildings and new environment/demographics; `State` adds owner-based aggregation. Generalizing geography must preserve object lifetime and aggregate consistency.
- **Registry locking and pointers:** `IdentifierRegistry`, production good pointers and demographic candidate pointers rely on stable lifetimes. Package hot-reload or save restore cannot silently invalidate them.
- **Employment/production/market phase order:** `InstanceManager::tick`, `MapInstance` employment phases and market callbacks determine available labor, actual acquisitions and next-day stress. Reordering can double-hire, double-clear, or remove the intentional lag.
- **Stored demographics versus people totals:** initialized POP/province structures currently have explicit consistency checks, not a complete shared transition API. Future population changes must not update only one representation.
- **One external output ceiling:** `ProductiveSiteUtilityResolver::apply` clears and sets `AggregateProducer`'s external ceiling. Another independent constraint writer could overwrite it; composition ownership must be explicit.
- **Multiple logistics paths and budgets:** explicit corridors, shared-capacity objects, graph routing and electricity/material flows coexist. A physical resource or shared edge must not receive independent duplicate budgets at integration seams.
- **Financial facts versus proxies:** `ProductiveSiteOperatingEconomics` aggregates cash facts with imputed costs. Treating its surplus as a bank balance would duplicate or invent settlement.
- **Accepted command versus world mutation:** the mobilization bridge logs before legacy queue execution, and jurisdiction identity is distinct from payload target. Future queue failures or target remapping require an explicit transaction/validation boundary.
- **Determinism beyond primitives:** country-relation pointer keys and non-generalized gameplay RNG cannot be copied into canonical persistence. Passing ECS worker-count tests does not resolve these other ownership concerns.

## Reusable Chassis

The following should **not** be rewritten without evidence of failure in a concrete vertical:

- `SimTime`, `Cadence`, `SimulationTimeline`, `SimulationEventScheduler` and their ordering/overflow/snapshot contracts.
- `ecs::World`, `SystemScheduler`, access declarations, command buffers, entity generations and tested worker-count invariants.
- Fixed-point arithmetic, typed indices, identifier registries and indexed maps, subject to documented range/lifetime limits.
- `AuthorityRegistry`, ordered accepted-command records, `PositionIdentity`/occupancy distinction and transactional timeline-command restore.
- Named deterministic RNG streams and canonical snapshot composition contracts; extend actual owner coverage rather than inventing a second runtime.
- `ProductionType::PROCESS`, `AggregateProducer::produce`, real building-level capacity and inventory mutation.
- `Pop::size`, native aggregation, `Pop::hire` and non-owning workforce adapters/competing-employer allocation.
- Explicit demographic profile reconciliation, nullable structures and load-lock-resolve provenance registry.
- Real market order/fill callbacks, resource buffers, directional access envelopes, transport capacities and `LogisticsGraph` conservation.
- Point-map/path search, reactive dirty recomputation, and bounded native causal-result snapshots.

“Keep” protects working mechanisms and invariants, not every current name, field owner, calibration or integration policy. Optional electricity/health/research capabilities can likewise be retained without making them universal state.

## Recommended Reconciliation Sequence

These are eight bounded follow-on increments, not authorization to implement them in this audit and not an exhaustive backlog. Respect the foundation freeze: each change must prove a concrete vertical need and retain one authoritative owner.

1. **Native capability composition proof:** expose one optional non-economy initialization capability through the existing `GameManager` native path. Prove presence/absence, validation and unchanged empty/native bootstrap. Do not design a universal package system or broaden all loaders.
2. **Position-to-target authority proof:** map one occupied-position mobilization request to its actual country target before admission. Prove equivalent human/AI grants, rejection of mismatched targets, and no log/queue mutation on rejection. Keep existing military mutation and registry owners.
3. **Geographic grouping boundary proof:** support one additional explicitly defined labor catchment in `ProductiveSiteBinding`/world resolution, reusing the same POPs and `allocate_competing_employers`. Prove overlap cannot double-hire and preserve ProvinceLocal behavior; do not replace Province/State.
4. **Optional population capability contract:** define and prove absence/presence semantics for one existing non-age-sex POP capability, with native size/employment unchanged. Document remaining mandatory dimensions explicitly. Do not add demographic evolution or a replacement population store.
5. **Production composition proof:** allow one additional site with a distinct PROCESS through current live orchestration and sanctioned inventories/market clearing. Prove physical conservation and no duplicate workforce allocation; do not rewrite clearing or build a universal economy graph.
6. **Military extension feasibility slice:** isolate one existing formation/type boundary and prove a chariot definition plus a modern formation definition against the same identity/group/resource-cost machinery. Explicitly identify remaining air/missile requirements; do not implement new combat or replace military storage wholesale.
7. **Restricted calculation proof:** evaluate one read-only, typed game-defined formula using explicit native inputs, deterministic limits and validation alongside the existing parser/registry machinery. Prove invalid operations fail without mutation. Do not equate the `EffectScript` success stub with execution or route all domain physics through scripts.
8. **One report continuity vertical:** deliver one delayed, position-addressed production observation using existing timeline events; preserve its observation time and report/knowledge state through a bounded continuity extension. Prove truth/observation separation and restore parity for that seam only. Do not claim a full intelligence model or full campaign save.

Full domain persistence, institution lifecycle, finance/tribute and advanced military mechanisms remain explicitly unresolved. The eight-step limit is not a claim that these eight increments complete both worlds. Later priorities should be reassessed against demonstrated vertical requirements rather than generating an indefinite foundation series.

## Scope Boundary

This audit makes no broad architectural code changes and no production-code changes of any size. It adds only this document. No tests are altered, no scenarios are built, no mechanics are implemented, no subsystems are renamed, and no legacy code is deleted. It creates no replacement actor, population, military, geography, economy or political system and no parallel authoritative state.

The two-world results are evidence-backed architecture judgments, not playable-scenario certification. The regression result above is the actual existing-build execution for this increment. No external mechanism or calibration is introduced; the framework and prior reference reviews inform evaluation, while repository implementation controls factual findings. Publication is limited to this document on the authoritative branch, following diff review; the completion report records the exact independently queried remote commit.
